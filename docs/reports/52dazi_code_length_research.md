## 0. 最重要的口径澄清（先读）

这是全报告最关键、也最容易被误解的一点，必须先讲清楚，否则第 ④ 节的数字会被误读。

| 口径 | 定义 | 单位 | 出处 |
| :--- | :--- | :--- | :--- |
| **52dazi 的「码长 / 均码」** | 平均每个字（含标点）所需**按键次数** = 总键数 / 总字数 | **键/字**（物理按键数） | `[来源: https://www.52dazi.cn/about, 抓取 2026-11-16]` |
| **52dazi 的「击键 / 均击」** | 每秒敲击按键的次数，是**速度**指标 | **键/秒** | `[来源: https://www.52dazi.cn/about, 抓取 2026-11-16]` |
| **空明码项目的「击 / 击数」** | 一次并击 = 双手同时各按一个码元 = **1 击**；击数 = ⌈码元数 / 2⌉ | **击/字**（并击次数） | `[来源: 项目 README.md 与 docs/reports/char_onehit_report.md, 读取 2026-11-16]` |

**结论（我的分析）**：52dazi 的「码长」是**单键口径**（按了多少次键），空明码的「击数」是**并击口径**（并击了多少次）。二者**不是同一个量，不能直接比较**。一次空明码并击会产生 2 个物理按键（左右手各一），但按项目口径只算 1 击。因此：

- 52dazi 记录榜上五笔/拼音用户的「平均码长」在 **2.2–3.0 键/字** 区间（第 ③ 节），这是**单键输入法**的现实基线。
- 空明码官方所称「理想平均码长 0.8/字」「极致码长 0.65」用的是**并击口径**（≈项目的 0.8 击/字），与 52dazi 的「码长」含义不同。
- 用户的目标 0.6–0.7 **击/字**是并击口径，比空明码官方「理想 0.8」更激进，逼近官方宣称的「0.65 极致码长」。

> ⚠️ 口径不可混用：不能把 52dazi 的「2.98 键/字」除以 2 当作「1.49 击/字」——五笔/拼音是顺序单键，其「键」并非可并行的「码元」，折算不成立（我的分析）。

## ② 指标定义（附原文引用）

### 2.1 站点自身说明（一手，最高优先级）

出处：`https://www.52dazi.cn/about` 页面「成绩指标含义」一节，抓取 2026-11-16。以下为**原文逐字引用**：

> - 标识：赛文标识，如`第999段`
> - 速度：每分钟输入的字数
> - 击键：每秒敲击按键的次数
> - 码长：平均每个字（含标点符号）所需要的按键次数
> - 理想码长：程序计算出的最短码长
> - 字数：文章总字数
> - 错字：结束时输入的错字数
> - 用时：总时间，单位秒
> - 暂停：打文时暂停的次数和总暂停时长
> - 键准：按键准确率，退格数及回改数作为失误按键来源，算法：`(总按键数 - 退格数 - 回改数 * 平均码长) / 总按键数`
> - 键法：左手与右手按键比率
> - 左：左手按键次数
> - 右：右手按键次数
> - 打词：有多少字是通过词组的方式输入的
> - 打词率：打词数占总字数的比率
> - 选重：要输入的字词不在首选位置的次数
> - 回改：输入错误被删除的字数
> - 键数：总按键次数
> - 退格：退格键被按次数
> - 回车：回车键被按次数
> - 重打：重新打的次数
> - 版本：版本信息
> - 输入法：所使用的输入法名称
> - 个性签名：个性签名
> - 哈希码: [小拆][xiaochai]的哈希码

`[来源: https://www.52dazi.cn/about, 抓取 2026-11-16]`

**字段自洽性验证（数据推定）**：记录榜第 1 名「平淡的一生」`totalKeyNum=12044850`、`totalWordNum=4044317`，`12044850 / 4044317 = 2.978 ≈ 2.98`，与其 `avgCodeLength=2.98` 一致 → 证实「平均码长 = 总键数 / 总字数」，即**按键口径**。`[来源: https://www.jsxiaoshi.com/index.php/Api/Rank/getRecordRank HAR, 抓取 2026-11-16]`

### 2.3 补充：同源/相关跟打器文档的更细定义（二手参考，非 52dazi 站自身）

`LightAPIs/ytgdq` 的 Score Info wiki（GitHub）给出了更细的算法说明，与 52dazi 定义高度一致但**不是 52dazi 官方页面**，仅作补充参考：

- 「理论码长（理论）：根据所设定的默认码表所计算出的码长值……开启`测词`开关时用所有词条计算，关闭时只用单字计算……若在设置中声明输入方案为**顶功类输入法**时，会采用较为极限的计算方法，得出的结果会比普通计算结果小许多。」`[来源: https://github.com/LightAPIs/ytgdq/wiki/Score-Info, 抓取 2026-11-16]`
- 「打词率：跟打中打词**字数**的比例，计算公式为：`打词的字数 / (总字数 + 回改)`。」`[来源: 同上, 抓取 2026-11-16]`
- 「效率：文段字数与输入上屏次数的比例……若跟打 20 个字只上屏 10 次（10 对词组），效率 = 200%。」`[来源: 同上, 抓取 2026-11-16]`
- 键准算法（第三方博客 Owen Yang《跟打器02 macOS使用指南》）：`(总按键数 - 退格数 - 回改数 * 平均码长) / 总按键数`；键法算法：`(1 - abs(左 - 右) / (左 + 右)) * 100`。`[来源: https://blog.owenyang.top/article/easy-typer-start-guide, 抓取 2026-11-16]`（**站点自身只说「比率」，此公式是第三方出处，标注为二手**）

> 「理论/理想码长」对**顶功/并击类方案**会用更极限的算法算出更小值——这解释了为何空明码这类方案在该站体系下「理论」值可能显著偏低（**数据推定**，未在 52dazi 上直接验证空明码账号的理论值）。

## ④ 对 0.6–0.7 击/字目标的量化启示

> ⚠️ 本节的门槛数字是**「我的估算」**——由「数据推定」的参数（项目内部单字结构 + 站点可得的定义）代入一个显式模型得出，**不是 52dazi 站点的实测结论**。52dazi 未提供任何并击方案的击数数据，无法直接验证这些门槛。

### 4.1 模型（我的估算）

沿用项目口径「击数 = ⌈码元数/2⌉」，设一篇文章：

- `p` = 打词率（**字数口径**，与 52dazi 定义一致：打词的字数 / 总字数）
- `c1` = 单字平均击数（每字至少 1 击，即 `c1 ≥ 1`）
- `cw` = 词平均击数，`cw = ⌈m/2⌉`，`m` = 词平均码元数
- `L` = 词平均长度（字/词）

则平均码长（击/字）：

```
K = (1 - p) · c1  +  p · cw / L
```

含义：`(1-p)` 的字按单字打，每字 `c1` 击；`p` 的字按词打，`pN` 字共 `pN/L` 个词，每词 `cw` 击，摊到每字为 `cw/L` 击。

### 4.2 参数取值依据

- `c1` 现状：按项目 `docs/reports/char_onehit_report.md`，前 1500 常用字「一击上屏 30.3% + 一击含空格 42.8% = 一次并击出 73.1%」，两次并击 26.9%。故 `c1 ≈ 0.731×1 + 0.269×2 = 1.269 击/字`。`[来源: 项目文件 docs/reports/char_onehit_report.md, 读取 2026-11-16]`
- `c1` 理想下限：`1.0`（所有单字都能一击上屏）。README 已实现「前 100 常用字 100% 一击」、`char_onehit_report` 前 1500 字 73.1% 一次并击出，是向 1.0 逼近的中间态。`[来源: 项目 README.md 与 char_onehit_report.md, 读取 2026-11-16]`
- `cw = 1`：要求词平均码元数 `m ≤ 2`（因为 ⌈m/2⌉=1 ⇔ m≤2），即「一词一击」，这是空明码「一词一码」的目标态。`[来源: 项目 README.md「一词一码」, 读取 2026-11-16]`
- `L`：二字词为主取 `L=2`，含更长词取 `L=2.5`。中文大词库实际词长通常 2 字居多。

### 4.3 现状自洽性校验（我的估算）

用 `c1=1.269`、`cw=1`、`L=2` 反推 README 所述 0.8 击/字对应的打词率：

```
0.8 = 1.269 - p(1.269 - 0.5)  ⇒  p = (1.269 - 0.8) / 0.769 ≈ 0.61
```

即在该模型下，**当前 0.8 击/字约对应 61% 打词率**（我的估算，非站点数据）。这个数量级合理（大词库并击方案打词率通常较高）。

### 4.4 达到 0.6–0.7 所需门槛（我的估算，核心结论）

**表 A：词平均 1 击（m≤2）、词长 L=2**

| 单字平均击数 c1 | 目标 K=0.7 所需打词率 p | 目标 K=0.6 所需打词率 p |
| :--- | ---: | ---: |
| 1.269（当前单字结构） | **≥ 74%** | **≥ 87%** |
| 1.0（单字全一击） | **≥ 60%** | **≥ 80%** |

计算：`K = c1 - p(c1 - 0.5)`；例如 `c1=1.0, L=2, K=0.7` → `p=(1.0-0.7)/(1.0-0.5)=0.60`。

**表 B：单字全一击 c1=1、词平均 1 击，词长变化**

| 词长 L | K=0.7 所需打词率 p | K=0.6 所需打词率 p |
| :--- | ---: | ---: |
| 2.0 | 60% | 80% |
| 2.5 | 50% | 67% |

计算：`K = 1 - p(1 - 1/L)`。

**三条可执行结论（我的估算）**：

1. **单字一击率是前提。** 若单字维持当前结构（`c1≈1.269`），要把整体压到 0.7 需打词率 74%、0.6 需 87%，门槛极高。若先把单字一次并击出率从 73.1% 提到接近 100%（`c1→1`），**仅此一项、打词率不变（61%）就可使 K 从 0.8 降到约 0.70**：`K=(1-0.61)×1 + 0.61×0.5 = 0.695`。这是性价比最高的一步。
2. **词平均码元数必须 ≤ 2。** 因为 `cw=⌈m/2⌉`，一旦词平均码元数 `m` 达到 3，`cw` 就变 2，此时即使打词率 100%、`L=2`，`K` 也 ≥ 1，**永远达不到 0.6–0.7**。所以「词基本都能一击（≤2 码元）」是硬性前提，打词率再高也无法弥补。
3. **打词率与词长共同决定下限。** 在 `c1=1, cw=1` 下，`K=1-p(1-1/L)`。要稳定落在 0.6–0.7，组合示例：`p≈70%, L≈2.2`（中位目标 0.65）；或 `p=61%, L≈3`（长词为主时约 0.6）。即**打词率 60%–80%、词长 2–2.5、词均 ≤2 码元**共同构成目标区间。

### 4.5 与站点数据的联系与边界

- 站点的**打词率定义**（「打词数占总字数的比率」，2.1 原文）与本模型的 `p` **口径一致**，因此若未来在 52dazi 用空明码账号实测，其「打词率」可直接代入模型验证 4.4 的门槛。
- 站点**不提供**并击口径的「击/字」实测（其「平均码长」是键/字），因此 0.6–0.7 目标**无法用 52dazi 数据直接证实或证伪**；只能用它校准打词率、码长基线等输入量。
- 空明码官方「理想 0.8、极致 0.65、熟练可保持 1 码长」的宣称（3.1/3.2）与本模型方向一致：0.6–0.7 属于「逼近极致」区间，需要接近满配的单字一击率 + 高打词率 + 短词码元，**容错空间很小**。
